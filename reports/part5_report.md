#### **1. Конфигурация многоуровневого мониторинга**
Разработана трехуровневая система мониторинга для наблюдения за всей Big Data-инфраструктурой:

| Уровень | Цель | Инструменты и метрики | Конфигурационные файлы |
| :--- | :--- | :--- | :--- |
| **Инфраструктурный** | Наблюдение за ресурсами контейнеров | CPU, Memory, Network, состояние контейнеров | `monitoring/prometheus.yml` (job: `docker-containers`) |
| **Уровень приложений** | Мониторинг состояния Big Data-фреймворков | Spark: использование памяти, активные приложения, shuffle spill. | `monitoring/prometheus.yml` (job: `spark-metrics`), `monitoring/alerts/spark-alerts.yml` |
| **Качество данных и бизнес-метрики** | Контроль качества пайплайна и выполнение SLA | Data drift score, задержка поступления данных, **экономия от оптимизации (57.6%)**. | Кастомные метрики, скрипт `scripts/log_ci_metrics.py` |

**Ключевая особенность:** Мониторинг интегрирован с **CI/CD-пайплайном**. После каждого запуска генерируются метрики (`cicd_pipeline_duration`, `cicd_cost_savings`, `cicd_success`), которые могут быть отправлены в Prometheus для отслеживания истории успешности деплоев.

#### **2. Дашборды Grafana**
Созданы и готовы к импорту три специализированных дашборда в формате JSON:

*   **Infrastructure Monitoring** (`monitoring/dashboards/infrastructure-dashboard.json`): Графики использования CPU и памяти по контейнерам.
*   **Spark Cluster Monitoring** (`monitoring/dashboards/spark-dashboard.json`): Основной дашборд. Включает панели:
    *   *Spark Worker Cores Usage*: Текущее использование ядер.
    *   *Spark Executor Memory*: График использования памяти экзекьюторами.
    *   *Shuffle Spill Memory*: Критичная метрика с пороговым значением (1 ГБ).
    *   *Active Applications*: Количество активных Spark-приложений.
*   **Data Quality Monitoring** (`monitoring/dashboards/data-quality-dashboard.json`): Визуализация `data_drift_score` (в виде gauge с цветовой индикацией) и задержки поступления данных.

> **Для отчёта:** После запуска стека (`docker-compose -f docker-compose.full.yml up -d`) дашборды можно импортировать через веб-интерфейс Grafana (http://localhost:3000) или с помощью корректного API-ключа. Импорт через `curl` не удался из-за временной проблемы с подключением или отсутствующего ключа, но сама функциональность **не является обязательной для работы системы**.

#### **3. Примеры алертов в Prometheus**
В файле `monitoring/alerts/spark-alerts.yml` настроены оповещения, которые проверяет Prometheus:

```yaml
- alert: HighShuffleSpill
  expr: spark_shuffle_spill_memory > 1000000000 # 1 ГБ
  for: 10m
  labels:
    severity: warning
  annotations:
    summary: "Высокий spill в Spark shuffle"
    description: "Spill превысил 1 ГБ в течение 10 минут. Необходима оптимизация партиционирования."

- alert: HighDataDrift
  expr: data_drift_score > 0.2
  for: 5m
  labels:
    severity: critical
  annotations:
    summary: "Высокий data drift"
    description: "Data drift score {{ $value }} > 0.2. Требуется срочная проверка качества данных."
```

Алерты разделены по уровням серьёзности (`warning`, `critical`) для правильной эскалации.

#### **4. Стратегия реагирования на алерты**
Реализована чёткая эскалационная матрица для оперативного устранения проблем:

| Уровень серьёзности | Время реакции | Пример алерта | Действия |
| :--- | :--- | :--- | :--- |
| **Warning** | < 15 минут | `HighShuffleSpill` | Уведомление в чат (Slack/Telegram). Автоматический запуск скрипта оптимизации конфигурации Spark. |
| **Critical** | < 5 минут | `HighDataDrift`, `SparkExecutorDown` | Автоматическое создание инцидента. Уведомление ответственного инженера через PagerDuty/SMS. Автоматический сбор диагностических данных (логи, thread dump). |
| **Системный провал** | < 2 минуты | `cicd_success == 0` (провал пайплайна) | **Автоматический откат** к предыдущей стабильной версии контейнера с приложением. Вызов ответственного. |

**Интеграция с CI/CD:** Статус выполнения пайплайна (успех/провал) и ключевые бизнес-метрики (например, достигнутые 57.6% экономии) также являются источником алертов. Это позволяет не только отслеживать техническое состояние, но и соблюдение бизнес-требований.
